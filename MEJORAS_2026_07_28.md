# CapitalQuant — Mejoras aplicadas (28 jul 2026)

Implementación real (con tests que pasan) de los puntos más críticos de la
Fase 1 del roadmap (`CapitalQuant_Auditoria_y_Roadmap.md`), priorizados por
riesgo de sobreajuste y de seguridad. Todo es retrocompatible: nada de lo
existente cambia de comportamiento a menos que se active explícitamente.

## 1. Purga y embargo en Walk-Forward (`optimization/walk_forward.py`)
- Nuevos parámetros `purge_pct`, `embargo_pct`, `max_lookback_bars`.
- `_build_windows()` ahora recorta el final de cada ventana de train
  (purga) y salta velas al inicio de test (embargo), evitando la fuga de
  información que un indicador de lookback largo (SMA200, etc.) podía
  producir en el borde train/test.
- Default no-cero (`purge_pct=0.02`, `embargo_pct=0.02`) para que el
  comportamiento "seguro" sea el default; se puede volver a 0 para
  reproducir corridas anteriores exactamente.
- Tests: `tests/test_hardening.py::test_wfo_*` (3 tests).

## 2. Modelo de costos realista (`core/costs.py` + `engine/backtester.py`)
- Nuevo `InstrumentCostProfile`: spread en puntos + comisión fija por
  lote + contract size, construible directo desde
  `MT5Provider.get_symbol_info()`.
- `BacktestConfig.use_realistic_costs` (default `False`, no rompe nada
  existente) + `BacktestConfig.cost_profile`.
- `BacktestEngine` reparte el costo mitad entrada / mitad salida, tal
  como se paga un spread real.
- Tests: `test_realistic_cost_profile_matches_manual_calc`,
  `test_backtester_realistic_costs_runs_without_error`,
  `test_backtester_default_pct_costs_unchanged` (verifica que el modo
  default sigue igual).
- **Pendiente para conectar end-to-end** (ver prompt de continuación):
  la UI todavía no expone un toggle para activar
  `use_realistic_costs` ni construye el `InstrumentCostProfile` a partir
  de `get_symbol_info()` automáticamente — hoy es una capacidad del
  motor, falta el cableado de UI.

## 3. Generalización cruzada de símbolos + estabilidad de régimen/estacionalidad
(`discovery/generalization.py`, nuevo módulo)
- `run_cross_symbol_generalization(strategy, datasets, origin_symbol, ...)`:
  re-corre la MISMA estrategia con los MISMOS parámetros sobre un dict
  `{símbolo: DataFrame}` y calcula qué fracción de símbolos (excluyendo
  el de origen) sigue siendo rentable → `generalization_rate` y
  `verdict()` ("GENERALIZA BIEN" / "GENERALIZACIÓN PARCIAL" / "NO
  GENERALIZA").
- `run_regime_and_seasonality_test(strategy, data, ...)`: corre una vez
  sobre todo el histórico y atribuye cada trade a (a) su mes calendario
  y (b) régimen ADX (tendencia vs. rango) vigente en la fecha de
  entrada, con veredictos `seasonality_verdict()` / `regime_verdict()`.
- Funciona sobre CUALQUIER `BaseStrategy` ya parametrizado — estrategias
  manuales, del Constructor, o exportadas del Hall of Fame vía
  `discovery/codegen.py` (que ya genera clases `BaseStrategy` reales).
- Tests: `test_cross_symbol_generalization_reports_rate`,
  `test_regime_and_seasonality_report_shape`.
- **Pendiente para conectar end-to-end**: falta el botón en la UI de
  Discovery ("Validar generalización") que tome una entrada del Hall of
  Fame, la compile con `codegen.py`, junte datasets de 8-15 símbolos vía
  `MarketDataProvider` y muestre el reporte — hoy es una API lista para
  usar, falta la vista.

## 4. Sandbox del Constructor de Estrategias reforzado con AST
(`strategies/ast_sandbox.py`, nuevo módulo + integrado en `code_compiler.py`)
- Segunda capa de defensa, además del regex existente (que se conserva
  sin tocar): camina el AST ya parseado y rechaza:
  - `import` / `from ... import` (a nivel de nodo, no de texto — no
    depende de cómo esté escrito el import).
  - Acceso a atributos dunder usados para escapar del sandbox
    (`__class__`, `__mro__`, `__subclasses__`, `__globals__`,
    `__bases__`, etc.), sin importar cómo se llegue a ellos en el texto.
  - `getattr(obj, "__subclasses__")` y variantes con `setattr`/`delattr`
    usando esos mismos nombres como string literal.
- Sigue siendo **defensa en profundidad para un único usuario local**,
  no aislamiento real de proceso — eso sigue pendiente si el roadmap
  avanza a multiusuario/API (Fase 4), tal como ya advertía la auditoría.
- Tests: `test_ast_sandbox_blocks_mro_escape`,
  `test_ast_sandbox_blocks_getattr_dunder_string`,
  `test_ast_sandbox_allows_normal_strategy_code`,
  `test_compile_strategy_code_rejects_mro_escape_end_to_end`.

## Lo que esta sesión NO tocó (ver prompt de continuación)
- Cableado de UI para los puntos 2 y 3 (el motor/API ya está listo).
- Optimización de portafolio (risk parity / mean-variance) — Fase 2.
- Panel de correlación entre estrategias del Hall of Fame — Fase 2.
- Toda la capa de ejecución (MT5 `order_send`, reconciliación, risk
  overlay, circuit breakers) — Fase 3, deliberadamente la más delicada
  y la que requiere más cuidado, no apta para hacerse apurado.
- FDR (Benjamini-Hochberg) además del DSR.
- CPCV (Combinatorial Purged Cross-Validation) completo — lo hecho aquí
  es purga/embargo simple, que es el primer paso pero no CPCV completo.
- Aislamiento real de proceso para el sandbox (Fase 4).
- Migración Streamlit → FastAPI + cola de tareas (Fase 4).
